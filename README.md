# Financial Statement Privacy Scrubber

## Github Repo 
Link : https://github.com/KHUBAIB-RAZA/PII-Scruber

A small FastAPI app that extracts PDF, DOCX, CSV, and TXT statements locally, replaces common direct identifiers, stores the combined scrubbed text in PostgreSQL, then sends only that scrubbed text to Groq's `openai/gpt-oss-20b` for an evidence-cited budgeting analysis. UK sort codes are redacted in labeled/compact and hyphenated forms. Legacy saved statements are scrubbed again before analysis retry or chat; if changed, old analysis is cleared and the corrected source is persisted before any provider request. Returned answers/evidence are also scrubbed and checked. Recurrence/frequency claims require citations containing at least two distinct dates. It accepts files from any bank without filename/bank-specific rules; multiple bank/account statement sections within one file are retained and labeled where recognizable headings are present. PDF page text, non-duplicated detectable table rows, widgets, annotations, DOCX body paragraphs/tables/headers/footers/comments/notes, CSV rows, and full text files are extracted locally. The browser shows the combined scrubbed extraction and analysis. Long statements are split into bounded requests; each response is validated against its exact source chunk, which is also a substring of the stored scrubbed text. The deterministic scrubber never calls an external service; identifiers in chat questions are scrubbed locally too. Pattern matching cannot guarantee detection of every country's identifier or every unusual formatting, so review displayed scrubbed output. Scanned PDFs require OCR and are explicitly marked (or rejected if no text is extractable); OCR is not yet implemented. Answers with unsupported numbers are rejected; this version does not calculate totals/counts/percentages.

## Architecture

- `app/extraction.py` handles offline PDF/DOCX/CSV/TXT extraction and generic section markers.
- `app/redaction.py` defines ordered, named `RedactionRule` entries and local identifier matching. The facade `app/scrubber.py` composes extraction/redaction for existing callers.
- `app/analysis.py` owns bounded chunking, shared pure prompt/payload builders, output schema/evidence/numeric/frequency validation, and analysis/chat orchestration. `app/provider.py` is the thin Groq SDK boundary; `app/llm.py` remains a compatibility import facade.
- `app/uploads.py` validates byte limits once and scrubs uploaded files locally. Both preview and legacy analyze routes use it.
- `app/repository.py` contains statement and chat persistence operations. `app/dependencies.py` owns the request-scoped SQLAlchemy session dependency; `app/main.py` defines HTTP routes.

Redaction is ordered by identifier specificity. Labeled UK sort codes are removed in compact, hyphenated, and spaced forms; ambiguous `NN-NN-NN` values are preserved only when they are valid common dates. Account and phone patterns are bounded to avoid consuming adjacent merchant/date/amount fields; masked card last-four values are retained. PDF table rows are appended only when their normalized cell sequence is absent from page text, reducing repeated prompt content without suppressing rows not represented in the text layer.

The browser uses a **scrub → save → preview → explicit send** workflow. Uploading through the UI does not call Groq: it stores only scrubbed text in PostgreSQL and displays the exact planned per-segment Groq request payloads (system/user messages, model, temperature, token cap, JSON mode, and the one-time plain-JSON recovery payload). It also estimates the initial request count and count including one JSON fallback per segment; adaptive recovery may use more, up to the hard run limit, and provider quotas may apply. Inspect a saved record by UUID without uploading again. Analysis is intentionally concise (up to two observations and evidence excerpts), not a full transaction listing; the UI shows whether each source segment completed, partially completed, or was not attempted, and points back to the full extracted scrubbed text. Chat questions also have a preview-and-confirm step: submit **Preview question for Groq**, review the preview, then click **Send this preview to Groq**. API errors are shown in the visible status and chat log. Aggregate requests such as monthly expense totals receive a clear local-only limitation response because this version does not normalize transactions or calculate totals; these prompts are not sent to Groq. For itemized support, ask which dated expense transactions are listed. Preview endpoints do not make provider/network calls. Other previews are generated by the same payload builders used by actual analysis/chat. PostgreSQL stores the scrubbed source, analysis and chat history; Groq receives only those constructed prompts containing scrubbed statement chunks and sanitized chat context, never raw files or database credentials.

Ambiguous unlabeled `NN-NN-NN` values are redacted unless they form a valid common date. A single transaction cannot establish a recurring weekly/monthly pattern; such model claims are rejected unless citations include at least two distinct dates.

## Run locally

1. Install Python 3.11+ and Docker Compose. From this directory, create and activate a virtual environment, then install dependencies:

   ```powershell
   py -m venv .venv
   .venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   ```

2. Start a real local PostgreSQL database:

   ```powershell
   docker compose up -d db
   ```

3. Configure the database and Groq key, then start the app:

   ```powershell
   $env:DATABASE_URL = "postgresql+psycopg://scrubber:local-dev-only@localhost:5432/scrubber"
   $env:GROQ_API_KEY = "your-key"
   uvicorn app.main:app --reload
   ```

4. Open http://localhost:8000. Upload via **Scrub, save & preview only**; this stores scrubbed text and displays the exact planned payload but does not call Groq. Inspect the content, then explicitly click **Analyze this saved statement with Groq**. For an existing UUID, use **Load saved preview**. Chat has the same preview-then-send confirmation. The Groq key is required only for analysis/chat. Scrubbed statements and chat history are stored in PostgreSQL `statements` and `chat_messages`. Do not expose the database port or use the example password on an untrusted network.

## Standalone local scrubbing

```powershell
python -c "from pathlib import Path; from app.scrubber import scrub_folder; print(scrub_folder(Path('data')))"
```

The function accepts a folder, processes all files recursively in sorted order, and returns a single string with a scrubbed per-file header. `app/schema.sql` documents the persistent schema; tables are also created at API startup.

## API

- `POST /api/statements/analyze` — multipart upload; scrub, persist, then analyze.
- `POST /api/statements/preview` — multipart upload; scrub and persist, then return the exact planned Groq payloads without calling Groq.
- `GET /api/statements/{id}` — retrieve scrubbed text and stored analysis.
- `GET /api/statements/{id}/groq-preview` — locally re-scrub and inspect a saved record plus the exact planned analysis payload; no provider call.
- `POST /api/statements/{id}/analyze` — retry/update analysis from the already-saved scrubbed text; does not create another statement.
- `POST /api/statements/{id}/chat-preview` — preview the sanitized question/history and exact per-segment chat payload without a provider call.
- `POST /api/statements/{id}/chat` — send a follow-up after preview; question/history are scrubbed before any provider call.
- `GET /api/statements/{id}/chat` — read stored conversation.
- `GET /api/health` — liveness endpoint.

Statement responses include `analysis_status` and `analysis_segments` coverage metadata; the latter contains only segment numbers, status, subchunk counts, and safe validation categories. Analysis preview responses also include `provider_request_estimate` with initial calls, the count if each segment uses its single JSON fallback, and the hard run limit; adaptive splitting can require more. `POST /api/statements/{id}/chat-preview` returns `local_only: true` and a user-facing explanation with an empty provider payload for unsupported aggregate calculations. The matching chat-send endpoint records and returns that local explanation without calling Groq.

The API persists scrubbed source before provider transmission, so it remains inspectable if analysis fails. The UI's preview flow is opt-in. The older `POST /api/statements/analyze` endpoint is retained for compatibility and analyzes immediately; prefer the preview route for interactive use. Analysis stops with a clear 413 if more than 32 chunks of at most 12,000 characters are needed; it never silently truncates. Lines are kept intact when possible, but an exceptionally long line can be split mid-line. The selected general chat/instruct model is Groq `openai/gpt-oss-20b`; from the supplied model list, it is the suitable analysis/chat choice. ASR, TTS, and prompt-guard models are not used. Provider free-tier access and quotas can change and were not live-verified.

To reduce `finish_reason=length`, prompts request at most two concise observations, a maximum 40-word answer, and two short exact evidence excerpts. Groq GPT-OSS requests set documented `reasoning_effort=low` and use `max_completion_tokens=1400`. Groq documents these controls for `openai/gpt-oss-20b`; see [Reasoning Models](https://console.groq.com/docs/reasoning). A response whose provider finish reason is `length` is accepted only if complete JSON passes the unchanged schema, evidence, number, identifier, and recurrence checks. Empty length responses and invalid JSON are split at line boundaries (whitespace/character boundary only if needed); request-too-large failures are also eligible for bounded splitting. Unsupported evidence/numbers/frequency and schema errors stop instead of spending more quota on failures splitting cannot resolve. Each run has a hard ceiling of 64 provider requests. At 128 characters or less, a chunk is not split further. Only fully validated subchunks are retained. If recovery fails or reaches its limit, saved analysis is marked **incomplete** with safe categories. There is no automatic retry for rate limits/server errors because it can worsen quota exhaustion; diagnostics direct users to wait or retry manually. Use **Retry incomplete analysis with Groq** on the saved statement; no re-upload is needed. Provider messages, statement content, and credentials are not exposed. The app has no authentication or multi-user isolation.

## Residual risks and next improvements

Regex cannot identify every country-specific or unlabeled identifier; review the preview before sending. Scanned PDF OCR is not implemented. Numeric claims are limited to explicit source numbers; deterministic transaction normalization/totals are future work. Highest-value improvements are locally run OCR with human verification, country-specific detectors with false-positive testing, structured transaction extraction and deterministic arithmetic, authentication/tenant isolation, and a documented retention/deletion policy.

## Submission artifact limitations

The package includes a demo recording script, not a recorded video. The transcript note and `prompts.txt` are not a complete export of the conversation event stream. No public repository was created because the task instructions prohibited publishing. These gaps are explicit and should not be treated as demonstrated live PostgreSQL/Groq/browser evidence.
